# Commit / PR / release / comment boundary hook (opt-in)

This hook closes the gap that issue #277 identified: the skill under-triggers not because its description is wrong but because skill selection happens turn-initially, while the highest-volume delegation moments — writing a commit message, a PR body, a release note — are turn-medial, the last sub-step of "implement X, commit, and open a PR". By the time the agent reaches that sub-step it is deep in execution and never re-runs skill selection, so it writes the message inline and the calibrated recipes go unused. No amount of instruction text in `SKILL.md` fixes a control-flow gating gap; a hook can, because it fires at the missed site, inside the harness, regardless of whether the agent reconsidered the skill.

The hook is `scripts/delegate-boundary-hook.sh`. It runs as a `PreToolUse` hook on the `Bash` tool. On every Bash call it cheaply checks whether the command is one of seven delegatable boundaries: a `git commit` (that authors a message, i.e. not `--amend`) → `commit-message`; a `gh pr create` / `glab mr create` → `pr-description`; a `gh issue create` with an inline body (`--body` / `-b` / `--body-file` / `-F`, not `--web`) → `github-issue-body`; a `gh release create` → `release-note`; an inline PR review-comment reply (`gh api .../pulls/<n>/comments -X POST`, the `/address-pr-comments` path) → `pr-review-reply`; a maintainer's PR review body (`gh pr review` with an inline body, or a `POST` to `.../pulls/<n>/reviews`) → `maintainer-review-reply`; or a general comment reply (`gh pr comment` / `gh issue comment` / `glab mr note` / `glab issue note`) → `maintainer-reply` for a short body, `maintainer-review-reply` for one at or above `DELEGATE_BOUNDARY_LONG_BODY_CHARS` (600) characters. The two reply boundaries are split because the recipes are: a review body carries a verdict and the anchors behind it at whatever length the evidence needs, while `maintainer-reply` is the closed two-sentence shape for a status comment or a diagnostic one-liner. That is also why the comment boundary routes by size rather than pinning one of them: the choice is between two shapes, and pinning the closed one is how it came to hold 33 of the corpus's delegations at 21% usable while its rejection reasons said the same thing over and over — two sentences returned where four paragraphs of evidence were wanted. The size is measured from the raw command (the scanner blanks quoted runs so a body is never read as live shell, which also means the classified segment carries none of it), from the file when `--body-file` names a readable one, and a measurement that fails leaves the short shape in place rather than promoting the reply on no evidence. `gh pr review` was added on 2026-08-26 after it turned out not to be a boundary at all — it cleared the pre-filter and matched no branch, so the most common way a maintainer posts a judgement produced no row and no reminder, while `maintainer-review-reply` sat at zero calls behind two rounds of prose routing. The review-comment boundary sat at 0/49 delegated until 2026-08-27, and the fault was the recipe rather than the sensor: `pr-review-reply` capped its output at the opener plus one short clause, while the 23 replies actually posted on PRs #440-#452 measure a median of 312 characters and only 4 fall under 100, so the recipe could not have produced 19 of them. The cap was lifted rather than the boundary retired. The read-only fetch step `gh api .../comments --jq …` is deliberately not a boundary — only an explicit `POST` counts. If the command is none of these, the hook exits immediately and does nothing. If it is, the hook derives the project the same way `delegate.sh` does, looks in `metrics.jsonl` for a delegation for that project **and this boundary's recipe** within the last few minutes, and records one `source:"opportunity"` row capturing whether the artifact was drafted locally (`delegated:true`) or is about to be written inline (`delegated:false`). The match is recipe-aware on purpose: matching on project alone let a `commit-message` delegation mark a later `gh pr create` or review-comment reply as captured even though the PR body / reply was written inline, which both inflated the trigger rate and suppressed the reminder (a `delegated:true` row skips the nudge). A bare delegation with no recipe no longer counts for any boundary — the calibrated recipe the reminder names is the path. When it was not delegated, the hook surfaces a one-line reminder naming the exact recipe to use — and for the boundaries whose recipe is proven it denies the call with that reminder as the reason until a delegation exists (#483, #521; see Modes).

Classification runs over a sanitised view of the command rather than the raw string. One awk pass drops heredoc bodies (resuming after the terminator, so a `cat > body.md <<'EOF' … EOF` write followed by `gh issue create --body-file body.md` still counts the post), blanks quoted spans, honours backslash escapes, and splits on `;`, `&`, `|`, `(`, `)`, `{`, `}` and newlines so each shell segment is classified on its own. Writing *about* a boundary command — in a heredoc body, a commit message, or any quoted prose — therefore no longer fires the hook, while wrapped forms like `sudo gh pr create`, `timeout 30 gh pr create` and `GIT_AUTHOR_NAME=x git commit` still do. Two cheap guards keep the cost off the common path: a single grep gates everything (an ordinary Bash call mentioning no boundary command costs one grep and exits), and the awk pass reads at most the first 32 KB of the command, because a 200 KB heredoc took ~800 ms to sanitise. The cap means a write-then-post whose heredoc body exceeds 32 KB — a long release note, say — records no opportunity row at all; the sensor goes blind rather than slow, which is the deliberate trade. A boundary command inside a wrapper script is invisible to that token classifier, and a wrapper is exactly what the worktree-isolation guard forces on a substitution-bearing call, so when the command runs `bash`, `sh` or `zsh` (optionally behind a leading `cd <path> &&`, interpreter options, or `/usr/bin/env`) on a readable script under a scratch directory (`$CLAUDE_JOB_DIR`, `$TMPDIR`, `/tmp`, `/private/tmp`, `/var/folders`; `DELEGATE_BOUNDARY_WRAPPER_DIRS` overrides the list) the script's text stands in for the command and is classified, measured and captured like any other, and the row carries `wrapper:"<path as written>"` (#469). The script is read, never run; a script anywhere else, including a repository's own test suite that commits inside a temp repo, is left alone, as is `bash -c "..."`.

Every boundary is counted the same way, whether the body is typed inline or read from a file. Between #355 and #465 a `gh`/`glab` post whose body came from an existing file (`--body-file`, `--notes-file`, `--file`, `-F`, including `gh api -F body=@draft.md`) was recorded with `state:"pre-drafted"`, did not nudge, and sat outside the trigger-rate ratio, on the theory that the drafting moment was an earlier `Write` often followed by human review. That exclusion was removed. The hook has no way to tell text a human approved from text the agent authored one Bash call earlier, which is exactly the case the sensor exists to catch — #358 makes the same argument — and the exclusion was not even applied consistently: writing the body and posting it in a single Bash call left the file non-existent at `PreToolUse` time, so the identical act was counted as a miss and nudged. The rate therefore moved with how the agent batched its shell calls rather than with its behaviour. A recorded delegation inside the window still wins: `delegated:true` marks the post as the success it is, so delegate-then-save-then-post is credited rather than counted against you.

A credited post is also where the shipped half of the ADR 0029 pair comes from for the reply recipes. `maintainer-reply` was the weakest recipe with any volume — 21% usable over n=33 — and the only one whose 32 rejections carried no captured final at all, because its output goes out inline inside `gh pr comment --body "..."` and never reaches a file `delegate-feedback.sh --final` could name. A commit message reaches one before `git commit -F` reads it; a reply does not. When a post is credited (`delegated:true`) it is by definition that delegation's shipped form, so the hook stores the body at `<data dir>/drafts/<stem>.final.txt` under the credited draft's own stem — oldest-unspent-first, matching the order a sweep posts in, so a whole afternoon of replies is not filed against one draft. `delegate-feedback.sh` adopts the file when the caller passed no `--final` and records `final_source:"posted"`; an explicit `--final` is never relabelled and never overwrites it — it is stored beside it as `<stem>.final.2.txt` (then `.3`, and so on), claimed by an exclusive create so parallel verdicts cannot take the same name (#474); the hook claims the bare name the same way, so a verdict and a post capture racing on one stem cannot overwrite each other either. An existing file is never clobbered by the hook. The capture is pre-post, so a post that then fails leaves a final for text that never shipped, which is what the marker is for. `DELEGATE_LOCAL_NO_METRICS=1` suppresses the capture along with the row. The scanner finds the body behind `--body`, `-b`, `--message`, `--body-file` and a bare `-F <path>`, and behind the `gh api` field flags `-f` / `-F` / `--raw-field` / `--field` when the key is `body` — `body=@path` names a file, any other key is not a body at all. Until 2026-08-28 it knew neither `-f` nor the `key=value` shape and read `-F in_reply_to=99` as a filename, so every reply posted the way `/address-pr-comments` prescribes yielded no text: the capture never fired once, no row in the corpus carried `final_source`, and all 37 finals on disk had been passed by hand (#461).

The reminder names a command that runs as printed. Every boundary recipe declares required inputs in its frontmatter and `delegate.sh` exits 2 when one is missing, so a reminder that named only the recipe — as it did until now — handed the agent `delegate.sh --recipe commit-message <tier> "..."`, which fails with `missing required inputs: recent_commits diff_stat why`. The hook fired, the agent tried the command, and the delegation never happened. The reminder now reads the recipe's own `inputs:` block and names each required key as a `--var`, renders `stdin` as an input redirection rather than a `--var`, omits inputs marked optional with a trailing `?`, and names the `prose` tier instead of a `<tier>` stand-in the agent had to guess. Reading the keys from the recipe rather than hardcoding them here keeps the reminder correct when a recipe changes its inputs.

The reminder names `--project <project>` explicitly. `delegate.sh` derives its metrics project from its own cwd, so an agent that `cd`s into the skill checkout to run the command records `project=delegate-local` and never matches this lookup — the nag-despite-compliance loop of issue #342. `delegate.sh --project NAME` and the `DELEGATE_PROJECT` environment variable both set it; `delegate-feedback.sh` copies the project off the delegate row it references, so the verdict lands on the same project without the variable (#474).

The project comes from the same `delegate_project_name` function (`scripts/lib/otel.sh`) that `delegate.sh` calls (`delegate-feedback.sh` derives nothing of its own and copies the field off the row it references), so the row the hook writes and the rows its lookup reads agree by construction: `DELEGATE_PROJECT` wins when set, otherwise it is the main repository's basename resolved through `git rev-parse --git-common-dir` so a linked worktree files under its repo, and a leading `cd <path> &&` retargets it to that repository (#385). Outside a git repository there is no project: the hook records the opportunity row with no `project` field rather than the cwd's basename, and credits a delegation that likewise carries none — but only one from the same session (#476). The metrics file is shared by every session on the machine, so "no project" is scoped by the `session` field `delegate.sh` writes from `CLAUDE_CODE_SESSION_ID` (#479) against the `session_id` in the hook's payload (the same transcript UUID); a projectless row from another session, or one with no session at all, credits nothing and the reminder fires. Credits are spent on the same terms, which is why the opportunity row records the session too. The reminder still runs as printed in that case — it renders `--project "<name>"` from a `--repo owner/name` on the command when there is one, since that is a lookup candidate, and otherwise omits the flag altogether, because a delegation issued from that same cwd and session is projectless and is exactly what the lookup matches, whereas one carrying any name could not credit the post. Before this, a session started in a parent folder of checkouts filed every boundary under that folder's name, a project that could never match a delegation and sat at rate=0% for good.

## Install

The hook ships with the skill but is not wired up automatically — enabling a global `PreToolUse` hook is your decision, so it is opt-in. Add the following to your global `~/.claude/settings.json`, merging the `Bash` matchers into your existing `PreToolUse` and `PostToolUse` arrays if you already have them. The `PostToolUse` entry is the spend confirmation described below (#497); install both, because without it a post the harness refuses keeps its credit spent and the retry is denied:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "bash ~/.claude/skills/delegate-local/scripts/delegate-boundary-hook.sh"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "bash ~/.claude/skills/delegate-local/scripts/delegate-boundary-confirm-hook.sh"
          }
        ]
      }
    ]
  }
}
```

Both hooks need `jq` on `PATH` (already a skill requirement) and nothing else. They fail open: any error, missing `jq`, or unparseable payload exits zero, so a hook bug can never block a commit. The only path that blocks a tool call is the deliberate deny described under Modes, and even that is issued only after `pick-model.sh` has confirmed a local provider is serving the recipe's tier.

## Modes

Since #483 the default depends on the boundary. `git-commit`, `issue-create`, `comment-reply`, `pr-review-comment` and, since #521, `pr-review-body` are denied until a delegation exists in the window: the hook returns `permissionDecision:"deny"` with the reminder as the reason, the agent drafts with the named recipe, reruns the same command, and the recorded delegation credits it. `pr-create` alone is warned: the same reminder arrives as non-blocking `additionalContext` and the post proceeds. The split follows the recipes. `commit-message` is 92% usable over n=41 and `github-issue-body` 100% over n=12, while `pr-description` is not yet above 80% on more than a handful of rows, and denying a post to hand the agent a recipe that fails half the time would teach it to route around the hook. The measurement behind the deny is the one in #483: 680 boundaries in 14 days, 108 delegated (15%), and after a warn-mode nudge the next boundary within 30 minutes was delegated 9% of the time against 34% after a credit. The nudge is delivered while the `git commit` it is about executes, so the text is already authored and posted by the time the agent reads it; with no human in the loop, only a mechanism that makes the agent redo the text with a draft moves the rate.

`pr-review-body` moved from warn to enforce in #521: warn mode measured 19% delegated, then 31%, then 0 of the next 4 — the nudge alone was not moving the rate, the same pattern that justified #483's deny for the other four boundaries. v0.36.0 shipped #514 (no retry when `no_context_echo` is the only failed check, `min_context_chars` raised to 900 on the recipe), and `maintainer-review-reply`'s post-#488 rows are 7 of 7 usable (all scaffold, n=7, as of 2026-09-16). The deny still keeps every fail-open path (`no-provider`, `no-model`, `retry-cap`, `metrics-unwritable`, `lock-timeout`), and the enforced set stays configurable per install via `DELEGATE_BOUNDARY_ENFORCE`.

`DELEGATE_BOUNDARY_ENFORCE` names the enforced set as comma-separated boundary names (default `git-commit,issue-create,comment-reply,pr-review-comment,pr-review-body`; an empty value enforces nothing). `DELEGATE_BOUNDARY_MODE=warn` and `=off` remain global overrides — `warn` downgrades every boundary to the reminder, `off` keeps recording the opportunity metric while silencing it entirely — and `=enforce` denies every boundary. The value is case-insensitive and anything other than those three is `warn`, as it was before #483. These are read from the hook's own environment (the `env` block of `settings.json`, or the shell Claude Code was started from), not from the command being judged: a `DELEGATE_BOUNDARY_MODE=off git commit …` prefix changes nothing, which the deny reason says. The credit lookup for a `comment-reply` boundary accepts either of its two recipes, `maintainer-reply` or `maintainer-review-reply`: the boundary names its recipe from the body's length, so a 700-character post denied under one name and redrafted at 450 characters would otherwise route to the other and be denied again.

A deny is never issued when it could not be acted on, and never becomes a permanent block. Before denying, the hook runs `pick-model.sh <tier>` for the tier the recipe declares (read by `recipe_tier` in `scripts/lib/recipe.sh`, the same expression `delegate.sh` uses) and, when that fails, warns instead and records why on the row: `enforce_skipped:"no-provider"` when nothing is reachable, `"no-model"` when a provider is up but serves no model for that tier, `"bad-tier"` when the recipe declares a tier `pick-model.sh` does not know. A session with MLX and Ollama down cannot delegate and must still be able to commit. The same fail-open covers the ways the credit itself can be impossible to record: `"metrics-unwritable"` when `DELEGATE_LOCAL_NO_METRICS=1` is set in the hook's environment or the metrics file cannot be appended to (a `DELEGATE_METRICS_FILE` that differs between `settings.json` and the shell means no delegation could ever be credited where the hook reads), `"retry-cap"` after two consecutive denials for the same session and boundary within the window, and only when the session recorded a delegation for the boundary's recipe after the streak began, whatever that delegation's exit status (a delegation that fails — a canary stall, an HTTP 500, the echo check — never credits, and that is the case the cap exists for; a credited or otherwise non-denied post resets the streak). A plain retry of the same command records no delegation and stays denied: until #511 two retries were all it took, and pr-agent's sweep session walked six undrafted replies through the cap in one evening by retrying each denied post twice, and `"lock-timeout"` when the lookup lock below could not be taken. The probe costs one `pick-model.sh` run, about 50 ms when the first provider answers and about the same when every localhost port is closed (a dead remote host costs `DELEGATE_PROBE_TIMEOUT`, 1 s, per entry), and it is paid only when a deny is otherwise about to happen — never on a warn-only boundary, a credited post, a body under the floor, or a capped session.

Lookup and row append are serialised with a `mkdir` lock (`.boundary-hook.lock` beside the metrics file). Two enforced boundaries running at once after one delegation used to both read the credit before either spent it, so one delegation credited two posts. The critical section is the lookup and, for a credited post, the `delegated:true` append that spends the credit — milliseconds. An uncredited post releases the lock before it decides whether it can be denied, so the provider probe never runs under the lock; a slow probe held there could have been stale-broken and let a second hook spend the same credit. A hook waits up to two seconds in 50 ms steps, breaks a lock older than five seconds (a killed hook; a lock left with no `ts` file by a hook killed between `mkdir` and the write is judged by the directory's own mtime), and if it still cannot take it proceeds unlocked and warns rather than denying. The lock carries an owner token, and a hook removes only a lock it still owns — so a hook whose lock was broken while it ran does not, on exit, remove the lock the next hook took in its place.

A body under the boundary's floor is neither nudged nor denied. Inline review comments ran at 3% delegated because most are one line — an applied-in hash, a dependabot rebase command, a one-word acknowledgement — and no recipe should draft those. The hook already reads the posted body for the ADR 0029 capture, so it records its length as `body_chars` (an integer, never the text) on every opportunity row whose body it can read at `PreToolUse` time, and marks a row under the floor `below_floor:true` so the data stays for tuning. The floor is per boundary: 20 characters for `git-commit`, because a one-line conventional commit is the `commit-message` recipe's own core output and one global 120 exempted every such commit from enforcement and from the denominator, and 120 for the rest; `DELEGATE_BOUNDARY_MIN_CHARS` overrides both. The body is read from the matched shell segment only, so `git commit -m "fix: x" && gh pr create --body "…"` measures the commit and not the PR body, and repeated `-m` are summed with a blank line between them, as git joins them. A relative `--body-file` is resolved against the payload's cwd, and against the target of a leading `cd <path> &&` when the command has one. A body-file path that opens with `$NAME` or `${NAME}` is resolved by looking the name up in the hook's own environment, which is the one the Bash tool inherits, so `body=@"$CLAUDE_JOB_DIR/tmp/reply.md"` is measured and captured; the lookup never expands or evaluates the text, and an unset name, a value that is not an absolute path, or any further `$` or backtick leaves the path unmeasurable (#489). An empty body the hook did read — `--body ""`, a readable empty `--body-file` — is a known 0-character post and records `body_chars:0` under the floor. A body the hook cannot know is not under any floor and is enforced as the mode says: a `git commit -F -` fed by a heredoc, a `--body-file` the same call is about to write, and any double-quoted or bare value carrying an unresolved `$`, backtick or `$(…)` — `--body "$(cat draft.md)"` and `-m "$MSG"` carry no `body_chars` and store no final, because the text they will post is not in the command. The one resolved shape is the `-m "$(cat <<'EOF' … EOF\n)"` form Claude Code commits with, whose heredoc body is the message; since #483 the scanner also reads `-m` and `-am`, so the length and the captured final are the message itself rather than its shell wrapper.

The look-back window for a prior delegation defaults to 480 minutes and is configurable with `DELEGATE_BOUNDARY_WINDOW_MIN`. The wide default exists for the batch flow, where a session delegates a sweep of drafts, waits for human approval, and posts hours later; a 10-minute window recorded every such post as a missed delegation and fired a spurious nudge at the compliant session. It is safe because credits are consumed: each `delegated:true` opportunity row spends one delegate row for that project and recipe, so one delegation credits one post rather than suppressing nudges for the rest of the window. The spend is paired at the post's own time: each credited post is replayed against the delegations inside its own window, oldest first, and the credit is the delegations no post consumed that are still inside the current window. Netting in-window delegations against in-window spends instead read a session that delegated, posted, and came back more than a window later as already spent, and denied it on the post after its next delegation (#503).

A spend is provisional until the call it paid for has run. The hook spends the credit at `PreToolUse` time, before the harness has decided whether the command executes, and two things routinely stop it: Claude Code's worktree-isolation guard refuses a command that carries a runtime value (`body=@"$CLAUDE_JOB_DIR/tmp/rr.txt"`) after the hook has already allowed it, and a `git commit` whose `git add` ran in a separate, refused call exits 1 on an empty index. In both the post never happened, the credit was gone, the retry seconds later was denied, and the corpus carried a `delegated:true` row for nothing plus a denied row for the same reply (#497; nine such pairs in the two days before the fix, retried 5 to 13 seconds after the credit). The hook cannot see either outcome, but the harness can: `PostToolUse` fires only when the tool ran and succeeded, a non-zero exit fires `PostToolUseFailure` instead, and a permission denial fires nothing after `PreToolUse`. So a credited post now leaves a marker — `<data dir>/.boundary-pending/<session>.<boundary>.<project>`, holding the call's `tool_use_id`, the recorded project, the credited draft's stem and the attempt's epoch — and `scripts/delegate-boundary-confirm-hook.sh`, the `PostToolUse` companion, removes it when a call with that `tool_use_id` succeeds (an interrupted call may or may not have posted, so it does not confirm). A marker still there when the same session reaches the same boundary for the same project inside 300 seconds is a post that did not happen, and the new call is it: it is credited on the same delegation, writes no second row, stores the draft's final from its own body — replacing one the hook wrote for the refused attempt (the marker records `captured`, and the marker proves that text never shipped), writing one where the refused attempt could not measure the body (the issue's first shape named its file through a variable the hook cannot resolve), and never touching a bare final it did not write, such as a verdict's explicit `--final` recorded while the marker was pending — and re-arms the marker under its own id, keeping the first attempt's epoch so a chain of refusals cannot extend the window. `PostToolUse` reports the whole call, and its status is the boundary's own only when the boundary is the call's last segment — `cd <path> && git commit …` and a wrapper script that ends in the commit both are, `git commit … && gh pr create …` and `git commit … || true` are not — so a marker is written only then; a boundary followed by anything else spends its credit for good, as before, and a retry that arrives in that shape consumes the marker rather than leaving it for a further post. The marker outranks a fresh credit, because a sweep that delegates again before retrying its refused post would otherwise spend the new delegation on the retry and be denied on the post it was for. It is honoured only once the confirm hook has been seen in the session (it creates `<session>.seen` on its first call): a `PreToolUse`-only install never confirms anything, and an unconfirmed marker there would credit every post after the first, which is the sweep the one-credit-per-post rule exists to stop. For such an install nothing changes. Stale markers are pruned after a day and `.seen` files after a week, so a session that outlives a day keeps its confirmation; both hooks resolve a relative `DELEGATE_METRICS_FILE` against the payload's `cwd`, so they share one pending directory. The harness runs non-read-only Bash calls one at a time (measured 2026-09-16: two `sleep 3` calls issued in one turn ran back to back), so by the time a second post reaches `PreToolUse` the first has been confirmed or refused, never in flight.

## Reading the trigger rate

Each boundary writes one opportunity row, so the denominator the whole problem is about — delegatable opportunities — finally exists. `scripts/metrics-summary.sh` reports it under a "Trigger rate (commit/PR/release/comment boundaries)" section, grouped by project, as `opportunities`, `delegated`, `missed`, and a `rate` percentage. Every posted boundary counts toward that ratio; the `state:"pre-drafted"` exclusion that ran from #355 to #465 is gone, so historical rates read lower than they used to (the 31 legacy rows in the corpus at the time became counted misses). Two kinds of row leave it since #483, and one line under the table says how many: `below_floor:true` rows (a body under the boundary's floor, which is not drafting) and `denied:true` rows the same session retried within the window — a retry being a later row (in append order, so a redraft in the same second counts) for that session, project and boundary that is itself a counted post, neither denied, below the floor nor a `retry-cap` fall-open (the post did not happen, and the delegated retry is the row that counts; counting the attempt too would record every enforced boundary as a miss followed by a hit). A denial that was never retried — or retried through something the hook could not see — stays in the rate as the miss it is. With the confirm hook installed, a credited post the harness refused and its retry are one row, not a credited row plus a denied one, so the excluded denials are the genuine ones: a post with no delegation behind it, redrafted and retried. An `enforce_skipped` row is a post that went through undrafted and counts as the miss it is. The footer names the floor in force (`DELEGATE_BOUNDARY_MIN_CHARS` when numeric, else the per-boundary defaults) and the retry window (`DELEGATE_BOUNDARY_WINDOW_MIN`), read with the same guards the hook applies. A project sitting at a low rate is one where commit, PR, and comment-reply artifacts are being posted without a credited delegation behind them, whether the body was typed inline or read from a file; that is the number to watch fall as the hook does its job. Rows recorded outside any repository carry no project and are listed on one `(no project)` line after the per-project rows, kept out of the count ranking so a scratch directory can never sit above a real project. The Grafana Overview dashboard charts the same population as a "Trigger rate" series (opportunities against delegated over time) with a range gauge beside it, from the opportunity rows `scripts/sync-metrics-to-loki.sh` pushes — with one simplification: LogQL cannot join a denial to its retry, so the dashboard leaves out every `denied:true` row, and its rate reads slightly higher than the summary's whenever denials went unretried. The opportunity rows store only the boundary type, the suggested recipe, the project and the session id (each when known), the delegated flag and, since #483, the body length and the `below_floor` / `denied` / `enforce_skipped` markers — never the command or the message text — so nothing sensitive lands in the metrics file.

## Uninstall

Remove the two `Bash` matcher blocks you added to `~/.claude/settings.json`. A `PreToolUse` hook left without its `PostToolUse` companion honours no marker from the next session on, since the `.seen` file is per session. The opportunity rows already written are harmless and are simply ignored once no more accrue; delete them from `metrics.jsonl`, and the `.boundary-pending/` directory beside it, if you want a clean slate.

# Verdict-sweep Stop hook (opt-in, Phase E)

The boundary hook above makes delegation more automatic, which is half the loop. The other half — recording whether the delegated output was actually used — is the agent's too: auto-delegation moved the decision-maker from the human to the agent, and the agent is the only party that knows whether it used an output — and only while it is still running. A `Stop` hook fits exactly there: it fires when the main agent finishes a turn, the agent is still alive, and the hook can hand the just-finished session's untracked delegations back to it for a verdict before it stops. It is the backstop for verdicts the agent did not record inline right after the call, which is the path SKILL.md teaches.

The hook is `scripts/delegate-verdict-stop-hook.sh`. On every `Stop` event it derives the current project (the same `delegate_project_name` that `delegate.sh` and the boundary hook call, so outside a repository it looks at projectless rows rather than a folder name) and scans `metrics.jsonl` for this session's successful delegations inside the look-back window that carry no verdict: delegate rows with `exit_status == 0` and no referencing feedback row, filtered to the project and to the session. `delegate.sh` records `CLAUDE_CODE_SESSION_ID` as `session` on every row (#479), the same value the `Stop` payload carries as `session_id`, and only a row whose session is this one is listed — the metrics file is shared by every session on the machine, and with no human sweep to pick them up, listing another session's drafts would ask an agent about output it never saw. A row with no `session` field is nobody's and stays untracked (#479 merged on 2026-09-12, so those rows are outside the 24-hour window anyway). "Carries no verdict" is decided by `otel_span_id` first and `ts` second (#481): a feedback row written since #479 carries `ref_id` and marks only its own delegation as tracked, so a verdict on one of two same-second siblings no longer hides the other. When the set is empty the hook exits immediately and does nothing. When it is non-empty it lists the batch (each delegation's pin, `ts`, `recipe`, and `tier`) and re-engages the agent with `{"decision":"block","reason":…}` — `decision:"block"` is what makes a stopping agent continue; plain `additionalContext` does not reliably re-engage it. The instruction asks the agent to record, for each one, whether it *used* the output as-is (hit), edited it and shipped it (scaffold), or rewrote/discarded it (miss) with `delegate-feedback.sh <pin> --source agent` followed by `hit`, `scaffold "<reason>"` or `miss "<reason>"`, printed as three complete commands; the pin on each batch line is `--id <otel_span_id>`, or `--ts <ts>` for a row with no span id, and a reason is required on scaffold and miss.

These verdicts carry `verdict_source:"agent"`, and they are the calibration signal (ADR 0030): the agent that used or rewrote the draft is the one judge there is, and the reason plus the stored draft/final pair is what a recipe edit is calibrated from. ADR 0015 had kept a separate maintainer tier as the headline hit-rate; it filled at a few rows a week, the live corpus holds none, and it was retired.

## Install

Like the boundary hook, this is opt-in. Add a `Stop` entry to your global `~/.claude/settings.json` (alongside the `PreToolUse` boundary-hook entry if you use it):

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "bash ~/.claude/skills/delegate-local/scripts/delegate-verdict-stop-hook.sh"
          }
        ]
      }
    ]
  }
}
```

The hook needs `jq` and `perl` on `PATH` (both already skill requirements). It fails open: any error, missing `jq`, unparseable payload, or an unwritable marker exits zero, so a verdict sweep can never wedge a session.

## The session-once loop guard

Because `decision:"block"` re-engages the agent, an unguarded hook would loop: if the agent declines or ignores the prompt, the next `Stop` sees the same untracked rows and blocks again, up to the turn limit. The guard is a session-once marker. The `Stop` payload carries a `session_id`; the first time the hook surfaces a batch it writes a marker file keyed by that id under `metrics.jsonl`'s directory (`.verdict-stop-markers/`). Every later `Stop` in the same session sees the marker and exits zero without re-injecting, so the agent always stops cleanly — even if it recorded nothing. The marker is written only when a batch is actually surfaced, so a session that delegated nothing leaves no marker and a later delegation in the same session can still be swept. Idempotency across sessions still holds: a recorded verdict drops its `ts` from the next scan, and per-session markers are pruned after seven days so they don't accumulate.

## Modes

The default mode is `warn`: the batch is surfaced once per session. Set `DELEGATE_VERDICT_STOP_MODE=off` to disable the hook entirely. There is deliberately no `enforce` mode — coercing a verdict is both hostile and dishonest, and a forced verdict is not a fact. The look-back window defaults to 24 hours; `DELEGATE_SWEEP_WINDOW_HOURS` sets it.

## Uninstall

Remove the `Stop` block from `~/.claude/settings.json`. The marker directory (`.verdict-stop-markers/` next to `metrics.jsonl`) and any agent-tagged feedback rows are harmless; delete the directory if you want a clean slate.
